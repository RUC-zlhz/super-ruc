### 2. 数据归档与空间管理

操作日志如果无限期存放在主表里，确实会导致 Kingbase 数据库的查询性能下降。

**需要修改的文字位置及方案：**

* [cite_start]**修改点 A：2.2 限制与约束 -> 审计约束** [cite: 80]
  * **【原替换文字】**：“审计约束：审批、配置、导入导出、通知发送、权限变化和敏感访问必须保留可查询日志，留存期不少于一个学期，**超期日志需提供定期自动清理或冷备份归档至历史库的机制，防止生产主表膨胀。**”
* [cite_start]**修改点 B：4.2 设计约束 -> 审计留存** [cite: 217]
  * **【原替换文字】**：“审计留存：关键审批、配置、导出和敏感访问记录至少保留 1 个学期，并支持按角色、时间和动作类型检索。**架构设计上需引入定时任务（如定期的冷数据迁移脚本），将超出保留期的数据从高频查询表中剥离。**”

*注：在你的具体代码实现时，这通常就是一个定时跑的 SQL 脚本，把旧数据 `INSERT INTO log_history` 然后 `DELETE FROM log_main`。*

### 4. 导入错误报告的可用性

**问题详细说明：**
假设负责老师整理了一份 100 人的党团信息 Excel 准备导入。其中第 45 行的身份证号少了一位，第 82 行的“入团时间”格式写成了文本。
如果系统只弹出一个红字提示：“导入失败：数据格式不正确”，老师就会崩溃，因为他需要在 100 行数据里挨个肉眼找错。这就叫“可用性差”。

**修改方案（业内标准做法）：**
系统发现错误后，**整批回滚**（这 100 条一条都不存进数据库），然后**生成一份新的 Excel 文件供老师下载**。这份 Excel 的内容和老师上传的一模一样，只是在最后一列加了一个名为“错误原因”的列，里面写着：“第45行身份证号长度校验失败；第82行日期格式无法解析”。老师只需下载这个文件，改掉这两处，重新上传即可。

**需要修改的文字位置及方案：**

* [cite_start]**修改点 A：3.1 软件功能概述 -> FR-009 文件导入导出** [cite: 139]
  * **【原替换文字】**：“导入导出需模板化校验、整批回滚和日志留痕。**当发生导入错误时，系统需提供带有具体错误原因（定位到行级与错误字段）的错误报告文件（或原样返回追加错误列的 Excel）供管理员下载修改。**”
* [cite_start]**修改点 B：4.1 性能要求** [cite: 213]
  * **【原替换文字】**：“标准格式 Excel 主数据 100 条批量导入应在 60 秒内完成成功提交或整批失败回滚，**并在回滚时输出可精确定位错误行的可下载错误报告**。”
* [cite_start]**修改点 C：4.2 设计约束 -> 文件交换** [cite: 217]
  * **【原替换文字】**：“文件交换：导入模板需固定字段结构；失败批次必须保障主库数据零污染（事务回滚），**并直接提供行级别的错误诊断依据（如行号与错因对应表），避免用户人工排查。**”

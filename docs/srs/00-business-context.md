## Business Principles

### BP-001: 官方口径优先

**Statement:** 所有政策咨询、流程说明与通知内容必须以学院或学校官方文件、标准答案或官方链接为依据。  
**Class:** Mandatory  
**Rationale:** 学生事务涉及资格、名额、流程、时间节点等敏感信息，错误答复会直接导致误办、漏办或投诉。

### BP-002: 模糊场景必须转人工

**Statement:** 当规则存在歧义、材料不完整或场景属于特殊个案时，平台必须将用户引导至人工咨询或人工审核。  
**Class:** Mandatory  
**Rationale:** 该平台是风险分流与效率提升工具，不应在高不确定场景下给出强结论。

### BP-003: 敏感数据最小暴露

**Statement:** 身份证号、生源地、户籍地、导师、休学/延毕等敏感字段必须按角色最小授权显示，并记录访问与操作日志。  
**Class:** Mandatory  
**Rationale:** 学生基础数据存在明确隐私与管理责任，越权查看或导出将引发合规与信任风险。

### BP-004: 不替代校级正式链路

**Statement:** 若某类事务依法规或校规必须在校级系统中生效，学院平台只能承担预检、引导、补件、归档或跟踪作用，不得宣称替代正式审批结果。  
**Class:** Mandatory  
**Rationale:** 当前已知无法直接对接“微人大”接口，必须明确学院平台边界，避免学生误判流程效力。

### BP-005: 移动优先、管理适配 PC

**Statement:** 学生侧高频轻量操作应优先适配手机端，管理员侧复杂查询、统计、导入导出与配置操作应优先适配网页端。  
**Class:** Guiding  
**Rationale:** 终端使用场景已明显分化，移动端更适合学生随时办理，PC 更适合管理端复杂任务。

### BP-006: 模板化优先、人工兜底

**Statement:** 所有结构化导入导出与文档解析应优先采用标准模板；模板不匹配或识别不稳定时，必须允许人工修正。  
**Class:** Guiding  
**Rationale:** 当前数据主要来自 Excel、Word、PDF，且 PDF/图片识别误差更高，标准模板是稳定落地前提。

### BP-007: 一期聚焦学院级全量需求交付

**Statement:** 一期建设范围以信息学院为边界，完整覆盖《需求文档.md》定义的学院级功能点；扩展到全校或引入更复杂跨学院业务应后置。  
**Class:** Aspirational  
**Rationale:** 项目当前更强调实用性和完整度，应先在学院边界内交付完整功能，再考虑跨学院扩展。

## Current Situation

### Current Process
学院学生事务当前主要依赖老师人工答疑、微信群转发通知、线下或半线下收集材料、分散文档与表格维护。学生常见需求包括党团流程查询、请假、盖章、开具证明、政策咨询、活动报名与材料提交。部分信息可以从学院现有数据表或官方文件获得，但整体缺少统一入口、统一留痕与统一权限控制。

### Pain Points
- 老师需要反复回答大量相似问题，事务性沟通成本高。
- 学生不了解办理条件、材料和时间节点，易漏办、误办。
- 通知分散在微信群、公众号、公开网站等多处，触达不精准。
- 请假、盖章、证明等常见事项依赖线下往返，状态不可追踪。
- 党团流程虽然规则较稳定，但当前缺少阶段化展示、提醒和记录。
- 数据来源以 Excel/Word/PDF 为主，格式不统一，更新责任不清晰。
- 敏感数据与操作留痕缺少统一平台级控制。
- 学业分析模块存在较高误导风险，无法直接给出强结论。

### Existing Systems
- 微信群 / 微信公众号：通知转发与日常沟通。
- 校级“微人大”及其他学校系统：存在正式业务链路，但当前无法直接接口对接。
- Excel 台账：学生基础信息、业务清单、统计数据。
- Word / PDF 文件：政策文件、模板、证明样式、表单材料。
- 学校公开网站：新闻、公开通知等官方信息来源。

### What Works Well
- 学院已经沉淀了较多政策文件、模板与结构化表格，可作为初始知识来源。
- 党团流程整体较稳定，适合沉淀为标准化内容与提醒节点。
- 管理端规模较小，便于建立明确责任人与维护流程。
- 一期并发规模虽低于校级平台，但验收基线仍需满足不少于 `50` 并发用户、核心学生事务 `95% < 3` 秒、核心管理操作 `95% < 5` 秒。

## Domain Boundaries

### In Scope
- 学院级政策知识库、FAQ、受控 AI 匹配答复与模板下载。
- 党团流程展示、进度查询、关键节点提醒、工作记录与理论自测。
- 请假、盖章、证明、报名、材料提交等常见事务申请与审批，以及证明自动生成与 PDF 预览。
- 学院通知汇聚、标签化管理与站内消息 / 邮件 / 短信定向推送。
- 学生基础数据、模板与业务台账的导入导出。
- 角色权限、字段可见性、操作日志与审计。
- 基于可核验数据的学业缺口展示、风险提示与课程类型级选课建议。

### Out of Scope
- 面向全校开放或支持非信息学院学生直接使用。
- 直接替代校级正式审批系统或声明学院平台审批具有校级生效力。
- 学生侧批量导入导出学院级数据。
- 依赖绕过反爬或非授权方式抓取封闭平台信息。
- 自动给出毕业资格、学分核算、选课人数竞争等强结论。
- 将助教纳入关键审批责任链。

### Adjacent Systems
- 微信实名体系：用于账号绑定与身份一致性。
- 人大金仓（Kingbase）数据库：业务数据与日志的核心存储。
- 学校公开网站 / 官方公众号：通知与政策来源。
- 校级正式系统：学院平台仅做引导、补件、归档或文件交换。
- 邮件 / 短信服务：通知外发渠道，短信可通过配置开关启用。

### Future Considerations
- 更细粒度的字段权限矩阵与审批矩阵。
- 更多学院事务模块，如出国申请、评优评奖细则、综合测评等。
- 与统一认证、教务系统或校级接口的正式集成（若后续开放）。
- 更完整的流程规则配置页、会签 / 联合审批机制。
- 更复杂的课程推荐规则、更多画像标签和跨学院扩展能力。

## Constraints

| Category | Constraint | Impact |
|----------|-----------|--------|
| Technical | 数据库需采用人大金仓（Kingbase） | 限制数据库选型与兼容性验证 |
| Technical | 无法直接对接校级“微人大”接口 | 必须依赖 Excel/Word/PDF 导入导出维持业务连续性 |
| Technical | 学生端与管理端使用场景不同 | 需要兼顾移动端便捷性与 PC 管理复杂度 |
| Technical | PDF/图片识别准确性弱于 Excel | 需要模板化约束与人工修正兜底 |
| Organizational | 管理端人员约 10 人，维护责任需明确 | 功能设计必须支持“谁上传谁维护”的轻运营模式 |
| Organizational | 助教不宜承担关键审批 | 审批链需集中在老师、班主任、领导与管理员 |
| Regulatory | 敏感学生信息需严格保护并最小化展示 | 权限、脱敏、审计、导出控制必须前置设计 |
| Operational | 官方信息源优先，非官方来源可能误导 | 抓取与问答都必须建立来源可信度边界 |
| Financial | 大模型调用与短信能力可能需要单独预算审批 | 需要预留成本控制、开关配置与替代通道，但相关需求仍需纳入系统规格 |
| Delivery | 项目更重视实用性、完整度与可演示性 | 一期需在学院范围内完整覆盖需求文档功能，并以五个核心闭环组织实施 |

## Success Criteria

| ID | Criterion | Measure | Target |
|----|-----------|---------|--------|
| SC-01 | 高频政策与流程咨询被自助化吸收 | 学期内老师人工重复答疑量下降 | ≥ 50% |
| SC-02 | 常见学院事务形成线上办理闭环 | 请假/盖章/证明/报名等事项线上提交占比 | ≥ 80% |
| SC-03 | 关键党团节点不再依赖人工口头提醒 | 关键节点提醒覆盖率 | 100% 目标对象 |
| SC-04 | 通知分发更精准 | 目标通知的误投/漏投反馈率 | ≤ 5% |
| SC-05 | 敏感数据管理合规可追溯 | 已授权操作均有日志；严重隐私事件 | 0 起 |
| SC-06 | 学生能更快定位本人办理状态 | 学生端可自查事务状态的事项覆盖率 | ≥ 90% 的核心事务 |
| SC-07 | 学院能形成客观工作记录 | 党团流程与审批操作留痕保留周期 | ≥ 1 学期 |

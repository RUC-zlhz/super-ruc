## 总体测试策略

1. 先验证资料完整性和入口可达性，明确 Web 管理端、小程序端、账号、密码、项目包是否齐全。
2. 先用文档提供的合法账号跑通核心正向流程，建立可用基线。
3. 再围绕边界输入、异常输入、权限边界、排序/查询/匹配、状态流转进行 Logic bug 专项。
4. 最后做白屏、服务中断、卡死无响应、未捕获异常、重复点击和大文件上传等崩溃类专项。
5. 每条候选 bug 都按模板补齐“问题描述、复现步骤、输入输出、证据、修复建议”，并对同根因去重。

## Logic bug 专项

| 编号 | 方向 | 第 14 组重点输入 |
| --- | --- | --- |
| L-01 | 权限边界 | 用 `teacher` 访问账号管理；用学生账号访问班团骨干或管理端能力；停用账号再次登录 |
| L-02 | 状态流转 | 证明申请重复提交、重复审批、审批后再次编辑、驳回后状态显示 |
| L-03 | 文档一致性 | PDF 说明的入口、菜单、字段、数据同步是否与实际一致 |
| L-04 | 查询/排序 | 通知发布时间、申请流水、学生列表、文件列表按时间或字段排序是否合理 |
| L-05 | 边界输入 | 空值、超长文本、特殊字符、重复学号、非法手机号、非法学分、非法文件类型 |
| L-06 | 跨端同步 | Web 发布通知、审批证明、维护党团阶段或培养方案后，小程序是否及时反映 |
| L-07 | 学业分析 | 上传无效 PDF、空 PDF、重复 PDF、非成绩单 PDF 后是否给出合理错误，不产生错误分析结果 |

| C-06 | 文件处理崩溃 | 上传非 PDF、损坏 PDF、非图片、空文件、超大附件，观察前后端是否崩溃 |

## 候选 bug 记录格式

- 编号建议：`BUG-G14-001`、`BUG-G14-002` 递增。
- 崩溃类证据：页面截图或录屏、Console、Network 状态码/响应体/耗时、刷新后恢复性结论。
- Logic 类证据：PDF 文档摘录、测试输入、实际输出、期望输出、页面截图或接口返回。
- 平台提交前必须去重：同一接口、同一按钮、同一校验缺失造成的同类现象只保留一条。
- 若问题只是文档已明确说明的已知限制，不提交为 bug；若文档未说明且导致无法运行或行为不一致，可以提交。

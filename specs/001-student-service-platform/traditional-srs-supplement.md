## 4.4 进度要求

### 4.4.1 一期开发周期假设

- **开发周期**：12 周
- **范围基线**：以知识库、流程、审批、通知、审计五个核心闭环作为实施主线，但必须完整覆盖 `需求文档.md` 中的全部功能点
- **边界说明**：学业模块、理论自测、短信通道、受控 AI 匹配、官方通知汇聚和证明 PDF 预览均属于一期范围；若真实业务数据暂未落实，可使用甲方确认的样例数据和开关配置完成交付与验收

### 4.4.2 里程碑计划表

| 里程碑 | 周期 | 目标 | 关联模块 | 对应 Customer Needs | 主要输出 |
|--------|------|------|----------|---------------------|----------|
| M1 启动与基线冻结 | 第 1-2 周 | 冻结全量需求范围、角色权限、审批边界、Kingbase 和离线流转基线 | 全局基线 | CN-008, CN-011 | 架构基线、数据库基线、字段权限基线、导入模板草案 |
| M2 知识库闭环完成 | 第 3-4 周 | 完成政策查询、模板下载、内容治理、受控 AI 匹配与来源版本化 | 知识库 | CN-001, CN-002 | 知识条目管理、模板管理、知识查询页面、受控 AI 匹配、来源治理能力 |
| M3 流程与审批闭环完成 | 第 5-7 周 | 完成党团流程跟踪、理论自测、常见事务提交、证明预览、审批工作台、驳回重提 | 流程、审批 | CN-003, CN-004, CN-005, CN-006, CN-007 | 党团阶段页、题库管理、自测页面、申请提交流程、证明预览、审核工作台、状态机与审批日志 |
| M4 通知与审计闭环完成 | 第 8-9 周 | 完成通知汇聚、标签化通知、站内 / 邮件 / 短信投递、导入导出、审计留痕 | 通知、审计 | CN-008, CN-009, CN-010, CN-011 | 通知来源治理、目标圈选、消息批次、导入导出批次、审计查询 |
| M5 联调与上线验收 | 第 10-12 周 | 完成全链路联调、学业分析、荣誉展示、学生画像、Kingbase 环境验证、部署和验收测试 | 全量模块 | CN-001 ~ CN-015 | 联调版本、荣誉榜单、画像视图、验收报告、部署手册、API 文档、数据库脚本 |

### 4.4.3 里程碑通过条件

| 里程碑 | 通过条件 |
|--------|----------|
| M1 | 架构确定为前后端分离；Kingbase 作为唯一数据库基线；校级 API 默认不可用的离线流转策略被确认 |
| M2 | 学生可完成“检索知识 → 查看来源 → 下载模板 → 受控 AI 匹配 → 转人工提示”闭环，内容具备版本和来源信息 |
| M3 | 学生可提交至少 3 类常见事务；证明场景可生成 PDF 预览；审批人可执行通过 / 驳回；理论自测可完成作答与留痕 |
| M4 | 管理员可完成 Excel 导入、通知汇聚与多渠道发送；所有关键动作进入审计日志；敏感字段权限规则生效 |
| M5 | 全量需求模块在 Kingbase 测试环境通过验收准则；学业弱提示、荣誉公示、学生画像均达到专题验收口径；源码、脚本、文档和部署说明齐备 |

### 4.4.4 延期处理原则

- 若 `M2` 延期，一期不允许直接跳过知识库闭环进入审批上线。
- 若 `M3` 延期，允许先演示党团进度查看和申请提交流程，但不得宣称审批闭环已交付。
- 若 `M4` 延期，通知和审计模块不得以“后补日志”方式上线。
- 若学业模块、短信或理论自测所需真实业务数据未到位，必须以甲方确认的样例数据、配置开关或模拟通道完成演示与验收，不得从规格中删除。
- 若荣誉或画像真实数据未到位，必须以甲方确认的正式样例荣誉清单、学籍样例和成长记录样例完成演示与验收，不得从一期范围中删除 `CN-014 / CN-015`。

## 4.6 验收要求

### 4.6.1 总体验收前提

- 验收环境数据库必须为 `Kingbase`
- 前后端分离部署完成，学生端与管理端均可访问
- 样例数据、模板文件、角色账号、审批链配置、荣誉样例清单和画像扩展字段样例完成
- 所有验收记录必须可回查到审计日志

### 4.6.2 知识库模块验收准则

**对应范围**
- 政策知识库 / FAQ
- 模板下载
- 内容治理

**对应 CN**
- `CN-001`
- `CN-002`

**验收准则**

1. 成功导入不少于 `50` 条知识条目，且每条均可显示标题、正文、官方来源、版本和更新时间，视为通过。
2. 对任意 `10` 条随机知识内容执行关键词检索，命中结果能够在 `3` 秒内返回且内容无乱码，视为通过。
3. 上传不少于 `10` 个 Word / Excel 模板后，学生端可成功下载并正常打开，文件内容不损坏，视为通过。
4. 将一条知识内容标记为“已停用”或“已过期”后，学生默认查询结果不再把该条目标记为当前有效口径，视为通过。
5. 对一条被标记为模糊场景的知识内容，页面必须显示“转人工”提示或对应入口，视为通过。
6. 对不少于 `5` 个咨询问题启用受控 AI 匹配时，系统返回内容必须包含标准答案或官方链接依据，不得出现无来源答复，视为通过。

### 4.6.3 流程模块验收准则

**对应范围**
- 党团流程可视化
- 党团节点提醒
- 常见事务在线提交中的流程展示部分

**对应 CN**
- `CN-003`
- `CN-004`
- `CN-005`

**验收准则**

1. 预置不少于 `30` 名学生的党团阶段数据后，学生端均可正确查看本人当前阶段、已完成节点和下一动作，视为通过。
2. 为党团流程配置不少于 `5` 个节点和对应提醒规则后，系统可自动生成待提醒清单，且不少于 `95%` 的目标对象被正确识别，视为通过。
3. 学生成功提交 `3` 类不同常见事务申请（如请假、证明、盖章）后，系统均生成唯一申请编号和初始状态，视为通过。
4. 对一个必须提示校级正式边界的事务类型，学生提交时系统必须显示“仅预检 / 归档 / 跟踪”边界文案，视为通过。
5. 若导入理论自测题库，不少于 `20` 名学生可完成在线答题并正确记录成绩、提交时间和题库版本，视为通过。

### 4.6.4 审批模块验收准则

**对应范围**
- 审批工作台
- 驳回 / 撤回 / 重提
- 证明开具与党团流程审批链

**对应 CN**
- `CN-006`
- `CN-007`

**验收准则**

1. 审批老师打开任意申请单时，必须同时看到申请详情、附件列表、历史动作和当前状态，且信息完整可读，视为通过。
2. 对不少于 `20` 条测试申请执行通过、驳回两类操作后，系统状态变更与审批意见保持一致，无错单、串单和状态错乱，视为通过。
3. 对至少 `5` 条被驳回申请，学生均可在原表单基础上修改并重新提交，且原始版本快照可追溯，视为通过。
4. 电子证明场景下，学生提交、班主任核验、团委老师审核、自动生成 PDF 预览、最终出件记录形成闭环且全链路留痕，视为通过。
5. 党团流程审批场景下，初审、复审、阶段更新和下一节点提醒能按审批矩阵顺序执行，视为通过。

### 4.6.5 通知模块验收准则

**对应范围**
- 标签化通知与定向分发
- 通知接收与查看

**对应 CN**
- `CN-009`
- `CN-010`

**验收准则**

1. 管理员可通过人工录入或受控抓取汇聚不少于 `20` 条官方通知，并创建不少于 `10` 条带标签通知，按年级、专业、角色筛选目标群体后，系统能正确展示目标范围人数，视为通过。
2. 向不少于 `200` 名样例学生发送通知时，非目标人群不得收到该通知，误投率应为 `0`，视为通过。
3. 目标学生登录后可在通知中心查看属于自己的通知，且能看到发布时间、标题和状态，视为通过。
4. 若启用邮件渠道，则同一批次通知至少 `95%` 的目标邮箱发送成功并可回查结果；若启用短信渠道，则同一批次短信发送结果必须完整留痕并可查看失败原因；站内通知必须完整可达，视为通过。

### 4.6.6 审计模块验收准则

**对应范围**
- 角色与字段权限控制
- 审计日志
- 离线文件导入导出

**对应 CN**
- `CN-008`
- `CN-011`

**验收准则**

1. 在 `Kingbase` 环境下成功导入不少于 `100` 条标准格式 Excel 主数据，且导入后中文字段无乱码、无部分提交、无主键冲突污染，视为通过。
2. 使用一份故意包含关键错误的 Excel 批次导入时，系统必须整批回滚并输出记录级错误报告，正式表不得出现部分成功写入，视为通过。
3. 对不少于 `20` 次关键动作（审批、配置、导入、导出、权限变化）进行抽查时，`document_audit_log` 中均可查到操作者、时间、对象和结果，视为通过。
4. 学生账号不得导出学院级原始数据；班主任和团委老师只能导出职责范围内汇总数据；高敏字段导出默认脱敏，视为通过。
5. 对不少于 `30` 条包含敏感字段的记录进行检查时，未授权角色页面不得出现完整身份证号等高敏信息，视为通过。

### 4.6.7 一期验收结论规则

满足以下条件，方可判定一期验收通过：

- 核心模块与专题能力的验收准则全部达标；
- 所有关键流程在 `Kingbase` 环境中验证通过；
- 离线文件流转具备“成功提交、失败回滚、错误报告、日志追溯”四项能力；
- 不存在未声明的校级 API 依赖；
- 学业模块必须提供弱提示能力、结构化规则导入能力和课程类型级建议；若真实业务数据不足，可使用确认过的样例数据完成验收，但不得缺失模块本身。
- 荣誉展示必须支持校级及以上正式荣誉的导入、公示、分类筛选、历史标注和隐私保护；学生画像必须支持权限内聚合展示、来源更新时间标注、本人查看和纠错申诉。

### 4.6.8 学业分析专题能力验收准则

**对应范围**
- 培养方案比对
- 成绩分析
- 课程类型级选课建议

**对应 CN**
- `CN-012`

**验收准则**

1. 导入不少于 `3` 个专业、`3` 个年级的培养方案规则后，系统能够生成模块级学业缺口结果，视为通过。
2. 导入或解析不少于 `30` 份标准成绩单后，系统可正确识别已修课程与缺口模块，且解析失败记录可回查，视为通过。
3. 当学期开课清单可用时，系统可针对缺口模块生成课程类型级建议，且页面不得展示动态选课人数或作出毕业结论，视为通过。
4. 学业分析页必须始终显示“仅供风险提示与辅助选课参考”的边界文案，视为通过。

### 4.6.9 奖励荣誉展示专题能力验收准则

**对应范围**
- 荣誉公示与榜样展示
- 荣誉分类筛选
- 荣誉数据维护与历史归档

**对应 CN**
- `CN-014`

**验收准则**

1. 成功导入不少于 `30` 条校级及以上正式荣誉记录，覆盖国家奖学金、校级优秀学生、学科竞赛等至少 `3` 种类别，视为通过。
2. 随机抽检 `10` 条荣誉条目，均可正确展示获奖者姓名、专业年级、荣誉名称、授予单位、文号或证书编号、公示日期及事迹摘要，视为通过。
3. 荣誉榜单支持按类别和学年筛选，筛选结果与导入记录一致，视为通过。
4. 已过期、撤销或归档荣誉默认不主动展示，历史查看页面标注“历史荣誉”，视为通过。
5. 获奖者已毕业或撤回授权时，详情页不得展示个人联系方式等敏感字段，视为通过。
6. 管理端可完成荣誉条目批量导入、单条录入、分类维护、展示有效期设置和归档 / 撤销操作，且维护人与更新时间可追溯，视为通过。

### 4.6.10 学生画像与信息管理专题能力验收准则

**对应范围**
- 学籍核心数据聚合
- 动态成长字段维护
- 画像权限、导出与纠错申诉

**对应 CN**
- `CN-015`

**验收准则**

1. 预置不少于 `50` 名学生的学籍主数据后，成功补录科研项目、学科竞赛、社会实践、志愿服务、学生干部任职等扩展字段各不少于 `20` 条，视为通过。
2. 辅导员登录后可正确查看所带班级学生的全景画像，学籍静态字段与动态成长字段聚合展示无错漏，视为通过。
3. 每项扩展字段均标注数据来源、录入人和最后更新时间，且管理端可导出权限范围内的画像快照，视为通过。
4. 辅导员越权查看非管辖学生时系统拒绝访问并记录日志，视为通过。
5. 学生本人登录后仅可查看本人画像，不显示录入人、来源系统等管理元数据，并可正常提交纠错申诉，视为通过。
6. 画像页面不得输出自动评分、排名或综合评价结论，涉及科研未公开成果、未获奖竞赛记录或个人敏感信息的字段必须按最小必要原则控制可见范围，视为通过。

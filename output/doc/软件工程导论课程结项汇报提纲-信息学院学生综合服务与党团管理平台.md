## 一、项目概述

### 1. 项目范围与主要功能

本项目是面向高校学院场景的一站式学生事务平台，覆盖学生端、教师/管理员端、后端 API、数据导入导出、审计与内网部署。仓库结构显示其为单仓全栈应用：`backend/` 为 FastAPI 后端，`web/` 为 Vue 管理端，`miniapp/` 为 uni-app 微信小程序学生端，`deploy/` 提供 Docker Compose、Nginx 和生产脚本。

已实现的主要功能可按六条闭环汇报：

| 闭环 | 学生/老师可见功能 | 代码证据 |
|---|---|---|
| 知识库闭环 | 政策知识查询、分类筛选、受控智能匹配、模板下载、后台知识维护 | `backend/app/knowledge/`、`web/src/views/knowledge/EntryList.vue`、`miniapp/src/pages/knowledge/index.vue` |
| 流程闭环 | 党团流程进度、理论自测、节点提醒、老师发起学生流程 | `backend/app/workflow/`、`web/src/views/workflow/PartyStageList.vue`、`miniapp/src/pages/workflow/` |
| 事务与审批闭环 | 请假/盖章/证明类申请、附件上传下载、驳回重提、证明 PDF 预览、审批工作台 | `backend/app/workflow/`、`web/src/views/approval/`、`miniapp/src/pages/request/` |
| 通知闭环 | 标签化圈人、发布发送、投递记录、学生收件箱、已读状态 | `backend/app/notice/`、`web/src/views/notice/NoticeList.vue`、`miniapp/src/pages/notice/` |
| 数据与学业闭环 | 文件导入导出、培养方案维护、成绩单 PDF 候选解析、学业缺口弱提示、运营看板 | `backend/app/exchange/`、`backend/app/report/`、`web/src/views/academic/`、`miniapp/src/pages/academic/index.vue` |
| 荣誉与画像闭环 | 荣誉公示、学生画像、纠错申诉、成长补录、画像快照导出 | `backend/app/honor/`、`backend/app/profile/`、`web/src/views/honor/`、`miniapp/src/pages/profile/` |

### 2. 部署方式简介

当前仓库支持以下部署和运行方式：

| 端 | 方式 | 说明 |
|---|---|---|
| 后端 API | FastAPI + Uvicorn | API 前缀 `/api/v1`，统一响应 `{code,message,data}`，健康检查 `/healthz` |
| Web 管理端 | Vue 3 + Vite 构建后由 Nginx 托管 | 管理端入口面向教师、辅导员、班主任、学院领导、超级管理员等角色 |
| 微信小程序学生端 | uni-app 构建 `mp-weixin` 包 | 权威验收口径为 `pnpm -C miniapp build:mp-weixin` |
| 内网生产 | Docker Compose | `web + backend + db + redis + minio` 五类服务，生产入口记录为 `http://10.10.0.13/` |
| 持续部署 | GitHub Actions self-hosted runner | `main` push 后由内网服务器 runner 执行构建、备份、迁移、种子和 smoke |

## 三、设计理念

### 1. 总体设计思想

系统采用前后端分离与模块化后端设计：

- Web 管理端负责教师/管理员的配置、审批、统计、维护。
- Miniapp 学生端负责查询、申请、进度查看、通知接收和个人画像。
- FastAPI 后端集中处理鉴权、权限、审计、状态机、数据一致性和第三方能力边界。
- 数据层以 Kingbase/PostgreSQL 兼容数据库为主，Redis 用于锁与缓存，MinIO 用于附件、模板和导出文件。

总体架构图源：`docs/source/diagrams/mermaid/course-final-architecture.mmd`  
SVG：`docs/source/diagrams/rendered/course-final/course-final-architecture.svg`

### 2. 用户体验设计

管理端采用企业后台风格：侧边导航、筛选区、表格、抽屉、状态标签、批量操作和结构化详情页，适合老师反复处理审批、通知、导入和维护任务。S75 中进一步加入首屏 loading、路由标题、顶部请求进度条、GET 去重和构建分包。

学生端采用微信小程序任务入口：首页聚合待办，底部 Tab 切换知识、通知、画像等高频模块；申请、流程、通知、学业等页面支持下拉刷新和明确反馈。S75 已激活多个页面的 `enablePullDownRefresh`，避免已有处理器成为死代码。

### 3. 关键设计决策

| 决策 | 原因 | 实现位置 |
|---|---|---|
| 权限与审计全部放在后端 | 前端隐藏不能作为安全边界 | `backend/app/core/dependencies.py`、`backend/app/audit/` |
| 学业模块只做弱结论 | 避免误导学生或替代教务最终审核 | `backend/app/report/`、`web/src/components/BoundaryAlert.vue`、`miniapp/src/pages/academic/index.vue` |
| 文件导入整批原子提交 | 主数据错误不能部分落库 | `backend/app/exchange/` |
| 生成式 AI 生产默认关闭 | 降低幻觉和不可控成本，一期保留受控检索 | `backend/app/core/config.py`、`backend/app/knowledge/` |
| 微信小程序为学生端权威形态 | 符合学生使用场景，H5 仅开发预览 | `miniapp/package.json`、主计划范围约束 |
| 内网生产采用 Compose + 自托管 runner | GitHub 公网 runner 无法直接访问内网服务器 | `deploy/intranet-prod/`、`.github/workflows/intranet-prod-deploy.yml` |

## 七、测试过程

### 1. 测试策略

| 层级 | 策略 |
|---|---|
| 单元测试 | 模板引擎、日期解析、上传限制、表单校验、PDF 解析等纯逻辑 |
| 集成测试 | FastAPI + 测试数据库，覆盖认证、知识、通知、申请、工作流、画像、荣誉、学业、审计等 |
| 性能/基准 | 学生导入 benchmark、热点查询 N+1 消除、Redis 缓存命中测试 |
| 构建测试 | Web `pnpm -C web build`、Miniapp `pnpm -C miniapp build:mp-weixin` |
| 生产 smoke | `/healthz`、首页、静态资源、公开知识路径、未登录鉴权边界 |

### 2. 测试环境与工具

- 后端：pytest、pytest-asyncio、ruff、py_compile/compileall。
- 数据库：本地 Docker 中的 Kingbase/PostgreSQL 兼容测试库 `sip_db_test`。
- Web：vue-tsc、Vite build。
- Miniapp：uni-app `build:mp-weixin`、产物风险扫描。
- 生产：`deploy/intranet-prod/scripts/smoke.sh` 和经 `ssh n150` 的内网只读回归。

### 3. 测试用例设计思路

- 按业务闭环设计：例如“圈人 -> 发布 -> 发送 -> 学生收件箱 -> 已读 -> 管理端回看”。
- 按权限边界设计：学生本人、辅导员、班主任、党团老师、超管、越权用户分别断言。
- 按异常输入设计：非法日期、无权限下载、无效分页、无效文件类型、未登录访问。
- 按回归缺陷设计：每个已确认 bug 尽量补定向测试，防止同类问题回归。

是否借助大模型：可汇报为“大模型辅助列测试矩阵、生成边界样例和初版回归脚本；人工根据业务规则筛选有效用例并执行验证”。

### 4. 测试执行流程

1. 本地静态检查：ruff、py_compile、vue-tsc。
2. 本地 DB 集成回归：启动 Docker 依赖后执行 pytest。
3. 前端构建：Web 与 Miniapp 分别构建。
4. 合并主线：解决冲突后重新跑整合验证。
5. 推送部署：GitHub Actions 自动部署。
6. 生产只读 smoke：健康、静态资源、公开接口和未登录保护接口。

## 十、遇到的问题

### 1. 技术与工具问题

- 本地测试库或 Docker 未运行时，DB 集成测试会被阻塞；解决方式是记录阻塞并在恢复后补跑。
- 生产网络曾出现代理污染风险；S42/S43 清理构建期和运行期代理边界。
- 微信订阅消息依赖用户在小程序授权；生产复测中未授权用户会返回微信 `43101 user refuse to accept the msg`。
- 小程序运行环境缺少 `Intl` 时会触发兼容问题；S73 已改为手写时间格式化。

### 2. 团队协作问题

- 多个 worktree、多个分支并行时容易出现冲突；S77 专门做 worktree 盘点、主线合并和生产回归。
- 互测反馈来自不同来源，需要区分有效 bug、重复问题、外部依赖和已修复项。

### 3. 过程管理问题

- 需求不断增量扩展，若只靠口头记录容易丢失；项目采用 `current-implementation-plan.md` 和 `refinements/` 做持久化计划。
- 文档与实现容易漂移；S71、S77 等节点都要求用代码、生产响应和测试结果回填文档口径。

### 4. 解决方案与经验教训

- 所有功能闭环都要有“代码 + 测试 + 文档 + 生产验证”中的至少一种硬证据。
- 对高风险功能坚持后端权限和审计，不把安全放在前端隐藏上。
- 学业、AI、微信等容易误导或依赖外部服务的能力，必须在界面和文档中说明边界。
- 先做小范围定向测试，再跑全量回归，最后做生产 smoke，是比较稳的交付节奏。

### 5. 其他问题

当前建议只人工确认三件事：

| 需要确认 | 建议处理 |
|---|---|
| 团队成员、汇报人、日期 | 填到首页和团队分工页即可 |
| 是否放真实截图/录屏 | 若现场网络或账号不稳，优先使用截图或短录屏 |
| 课堂是否要求沿用老师给的基础需求原编号 | 若要求，将本提纲的 `FR-001 ~ FR-018` 映射回课堂编号 |

若老师明确要求“代码行覆盖率”，再额外引入 coverage 工具重新执行测试；当前仓库已有功能测试和构建结果，不建议在 PPT 中虚构覆盖率百分比。
